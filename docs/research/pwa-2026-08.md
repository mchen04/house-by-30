# PWA launch, cache, and update research

Last reviewed: 2026-08-23

## Decisions

House by 30 stores public files in Cache Storage. It stores private account data in account-scoped IndexedDB.

| Concern           | Decision                                                                                                  |
| ----------------- | --------------------------------------------------------------------------------------------------------- |
| Launch            | Serve the versioned shell from Cache Storage. Refresh it in the background.                               |
| Private data      | Read matching IndexedDB data while `/api/bootstrap` runs. Never cache API responses in Cache Storage.     |
| Account isolation | Compare the cached session UUID with a server-set owner hint before private paint.                        |
| Edits             | Write IndexedDB and the outbox before network delivery. Keep the existing field-level conflict rules.     |
| Reconnect         | Drain in the foreground on `online`. Do not depend on Background Sync.                                    |
| Navigation        | Preload initial static files during worker install. Preload rare screens only after the account is saved. |
| Updates           | Check on launch, reconnect, page restore, visibility return, and a one-hour interval.                     |
| Activation        | Activate automatically only when the page has no open or undurable edit.                                  |
| Old pages         | Keep old static caches until every live page reports the current build.                                   |

## Current platform guidance

- The [Next.js PWA guide](https://nextjs.org/docs/app/guides/progressive-web-apps) requires a manifest and a registered service worker. It also recommends secure update handling.
- The [Next.js SPA guide](https://nextjs.org/docs/app/guides/single-page-applications) and local prefetch guide support lazy code and deliberate prefetch.
- The [service worker lifecycle guide](https://web.dev/articles/service-worker-lifecycle) explains install, waiting, activation, and client control.
- The [Workbox update guide](https://developer.chrome.com/docs/workbox/handling-service-worker-updates) warns that forced activation can mix page code and worker code.
- [Navigation preload](https://developer.mozilla.org/en-US/docs/Web/API/NavigationPreloadManager) starts a navigation request while the worker starts.
- [Background Sync](https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API) still has limited browser support. It cannot be the only reconnect path.
- The [offline data guide](https://web.dev/learn/pwa/offline-data) assigns structured data to IndexedDB.
- The [Service Workers specification](https://www.w3.org/TR/service-workers/) leaves cache versions and deletion to the application.

## Local reference project

The local Splitwisest project supplied four useful ideas.

- Change worker bytes for every build.
- Check for updates on browser lifecycle events.
- Guard reload loops and undurable input.
- Keep old static files while old pages can still request them.

House by 30 does not copy Splitwisest's private response cache. Its private data model already uses account-scoped IndexedDB and a durable outbox.

## Rejected options

- Shared Cache Storage cannot own private JSON. A service worker cache is origin-wide.
- Network-first navigation delays every installed launch.
- Immediate cache deletion can break an old page's lazy chunk.
- Forced reload can lose an input buffer or a pending IndexedDB write.
- Background Sync alone excludes browsers that do not implement it.
